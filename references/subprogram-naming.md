# 子程序命名：树上短标题，说明进批注

> 一句话结论：`LAB` 名只放 1~6 位 ASCII 代号；程序树标题只放
> `【分类】-短主题`；职责、触发条件、互锁、参数和 I/O 清单放进批注或
> 程序体头部，不要塞进标题。

---

## 1. 现场样本

两份真实机台备份的写法一致：

- `LAB` 名是 `1`、`2` … `12`，不是中文，也不是句子；
- `LAB` 前一条 `ct=3` 注释是程序树标题；
- 标题长度 9~13 个字，统一为 `【分类】-短主题`；
- LadEditor 在标题后自动补 `(1)`、`(9)` 这类程序编号。

典型标题：

| 标题 | 字数 | 说明 |
|---|---:|---|
| `【外部端子】-IO點` | 10 | I/O 点位集中映射 |
| `【面板功能】-模式與倍率` | 12 | 面板开关与倍率选择 |
| `【系統功能】-主軸` | 9 | 主轴相关逻辑 |
| `【刀庫】-伺服刀庫` | 9 | 伺服刀库换刀 |
| `【刀庫】-普通刀庫` | 9 | 普通刀库换刀 |
| `【系統功能】-急停抬刀檢測` | 13 | 急停后的抬刀检测 |

`(1)`、`(9)` 是 LadEditor 根据 `LAB` 名生成的序号，不是标题的一部分。

---

## 2. 三层的职责

| 内容 | 写在哪里 | 规则 |
|---|---|---|
| 程序标识 | `programs[i].name`（`LAB`） | `MAIN` 或 1~6 位 ASCII 字母/数字，如 `1`、`MAG1` |
| 程序树标题 | `programs[i].comment` 第一行 | `【分类】-短主题`，建议 ≤20 字，不换行、不带序号 |
| 程序批注 | `comment` 第二行起 | 职责、调用条件、互锁、参数、I/O、版本差异 |
| 段功能 | `networks[j].comment` | 一条 `type-1` 注释，说明这一段的输入、输出和目的 |
| 元件用途 | `variables` 的 `short` / `long` | `type-4` 元件批注，短名 4~8 字，长说明一句 |

如果现场习惯不使用多行 `ct=3`，把详细说明放到程序体第一条
`type-1` 注释里，效果相同；**唯一不能妥协的是程序树第一行必须是短标题**。

---

## 3. 标题规则

1. **只写名词短语**：写“做什么”，不写“什么时候、因为什么、接下来怎样”。
2. **必须有分类前缀**：`【外部端子】`、`【面板功能】`、`【系统功能】`、
   `【刀库】`、`【报警】`、`【M码】`、`【润滑】`、`【液压】`、`【排屑】`、
   `【主轴】`、`【冷却】`、`【安全】`。
3. **分隔符统一用 `-`**（全角 `－`、破折号也可接受），不要用冒号或逗号。
4. **≤20 字**：超过就说明把说明写进标题了。
5. **不带编号**：不要写 `(1)`、`1.`、`一、`；LadEditor 已经显示程序号。
6. **不用句读**：标题里不出现 `，。；！？、`；这些是批注的标点。
7. **不写版本和日期**：修改日期、`V2`、`修改版` 都放到批注。
8. **程序名不写中文**：`刀库`、`换刀逻辑` 都不能作为 `LAB` 名。

## 4. 好例与坏例

好：

```json
{
  "name": "9",
  "comment": "【刀库】-伺服刀库\n职责：刀盘旋转、刀套翻转与换刀完成确认\n调用：M06 且主轴停止、刀库门关闭\n互锁：急停、刀库未原点、气压不足时禁止启动\n参数：R120~R139 刀号与刀套映射",
  "networks": []
}
```

坏：

```json
{
  "name": "SERVO_TOOL_MAGAZINE_CHANGE_LOGIC",
  "comment": "当刀库计数到达设定值后自动切换到下一刀位并输出提示，同时检查主轴停止和刀库门关闭",
  "networks": []
}
```

问题：`LAB` 名超过 6 位且带下划线；标题是一整句；调用条件、互锁和提示
全部挤在树上，旁边的程序名会被挤到看不见。

## 5. 工具如何检查

`plan-lint` 在编译前检查每个子程序：

| 规则 | 级别 | 触发条件 |
|---|---|---|
| `program_name_invalid` | error | `LAB` 名不是 1~6 位 ASCII 字母/数字 |
| `program_title_missing` | warning | 子程序没有 `comment` |
| `program_title_too_long` | warning | 第一行超过 20 字 |
| `program_title_numbered` | warning | 第一行以 `(1)`、`1.`、`一、` 开头，或以 `(9)` 结尾 |
| `program_title_sentence` | warning | 第一行含 `，。；！？、` |
| `program_title_without_category` | warning | 第一行不是 `【分类】-...` |

只检查第一行，所以多行批注不会被误报。`error` 会阻止 `build`；
`warning` 不阻止，但交付前应清零。

```bash
python scripts/run_syntec_lad.py plan-lint my.plan.json
```

---

## 6. 为什么模型以前总写长句

不是模型“不会概括”，而是旧约定给了它三个错误信号：

1. Plan Schema 只有 `comment` 一个标题字段，文档只写“程序头注释，
   最长 255 字符”，没有规定第一行必须是短标题；
2. `SKILL.md` 要求程序头记录“标题、修订历史、参数、I/O 速查、注意事项”，
   模型就把这些内容一起写进 `comment`；
3. `plan-lint` 完全没有子程序命名规则，长句不会收到任何反馈。

现在的约定把字段拆成“第一行标题 + 后续行批注”，并让 `plan-lint`
在生成前给出可执行的修改建议。

---

## 7. 反模式

- 把 `LAB` 名写成 `TOOL_MAGAZINE`、`换刀` 或 `9-伺服刀库`；
- 标题写成“当……时，先……再……最后……”；
- 标题里带 `(9)`，树上变成 `(9) (9)`；
- 为了短而短，把不同功能都叫“辅助”，后人无法区分；
- 只写短标题，不留任何职责和互锁说明。
